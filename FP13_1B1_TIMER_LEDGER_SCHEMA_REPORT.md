# FP-13.1B1 Timer Ledger Schema Report

## Overview
This report details the implementation of Phase 1 (FP-13.1B1) of the timer ledger rollout, strictly fulfilling the requirement to add the database foundation for the timer ledger without wiring any runtime business logic. 

## Models Added
Two new models were added to `schema.prisma`:

### 1. `TicketTimeLog`
A highly granular table to track chronological blocks of productive or paused time. 
- Fields: `id`, `ticketId`, `userId`, `stage`, `ownerType`, `source`, `startedAt`, `endedAt`, `durationSeconds`, `countsAsWork`, `pauseReason`, `workSessionId`, `breakLogId`, `createdAt`, `updatedAt`.
- Enums avoided: `stage`, `ownerType`, `source`, and `pauseReason` were mapped as `String` to prevent DB-level enum migration risks.
- Relations established to `Ticket`, `User`, `WorkSession`, and `BreakLog`.

### 2. `ReviewCycleLog`
A macro-level table to permanently track iterative review cycles and rework decisions.
- Fields: `id`, `ticketId`, `cycleNo`, `assigneeId`, `reviewerId`, `reviewStartedAt`, `reviewEndedAt`, `decision`, `feedback`, `assigneeWorkSeconds`, `reviewerWorkSeconds`, `reworkStartedAt`, `reworkEndedAt`, `createdAt`, `updatedAt`.
- Constraints: Added a unique compound index on `@@unique([ticketId, cycleNo])`.
- Relations established to `Ticket`, and optional relations to `assignee` (`User`) and `reviewer` (`User`).

## Fields Added to Existing Models
- `Ticket`: Added `reworkCount Int @default(0)`, `timeLogs TicketTimeLog[]`, and `reviewCycles ReviewCycleLog[]`.
- `User`: Added `ticketTimeLogs TicketTimeLog[]`, `assigneeCycles ReviewCycleLog[]`, and `reviewerCycles ReviewCycleLog[]`.
- `WorkSession`: Added `ticketTimeLogs TicketTimeLog[]`.
- `BreakLog`: Added `ticketTimeLogs TicketTimeLog[]`.

## Migration Safety
- **Migration Name:** `add_ticket_timer_ledger` (Specifically `20260601074929_add_ticket_timer_ledger` dynamically generated by Prisma).
- **Additive Only Confirmation:** This migration is strictly additive. No existing columns on the `Ticket`, `User`, `WorkSession`, or `BreakLog` tables were dropped or modified (other than adding reverse relation arrays for Prisma). The new schema is entirely decoupled from existing `tickets.service.ts` logic.
- **Service Logic Confirmation:** I explicitly confirm that no service logic was wired. `TicketsService`, `WorkdayService`, and `TicketTimingService` remain exactly as they were in FP-13.1A.

## Risks Remaining for FP-13.1B2 / FP-13.1C
1. **Concurrency:** When wiring business logic in FP-13.1B2, race conditions might occur if a user aggressively pauses and resumes work. A robust lock or `findFirst` check must be implemented to ensure only one active `TicketTimeLog` (where `endedAt` is null) exists per user/ticket.
2. **Workday Drift:** In FP-13.1C, if a user's workday is forcefully terminated (e.g., via the midnight auto-close cron in `SchedulerService`), the integration must cleanly hook in to also forcefully close any open `TicketTimeLog`. Neglecting this will result in massive unclosed timer blocks.
